# 管理后台

适用页面为 `/admin`，本次局部完善依据 [后台管理流程完善](../../specs/changes/admin-management.md)。实现沿用现有浅色、蓝紫色主操作、侧栏导航和紧凑表格；本文记录后台现有行为及样式证据，范围限于后台功能。

## 页面边界与权限

页面使用 `requireAdmin`；所有管理 API 使用 `authenticateAdmin`，保持匿名 401、普通账号 403 和数据库不可用 503 的既有契约。页面未登录时跳转登录页，普通账号进入后台时返回首页。

客户端只用 `import type` 引用 `lib/admin.ts` 的数据类型，构建时擦除，不把 `cloudflare:workers` 引入浏览器。界面由 `app/admin/admin-console.tsx` 与 `app/admin/admin.css` 实现，使用独立后台外壳。

## URL 与关联导航

`AdminConsole` 在挂载时读取查询参数，并监听 `popstate` 恢复栏目和关联条件；导航调用 `history.pushState`，支持浏览器前进、后退、直接打开链接和刷新恢复。

| 参数 | 行为 |
| --- | --- |
| `tab` | 支持 `overview`、`users`、`mistakes`、`uploads`、`system`；缺失或无效时显示数据概览。 |
| `userId` | 初始化内容管理的用户条件；用户列表的错题数量入口跳转到该用户的错题。 |
| `uploadId` | 初始化上传批次条件；上传列表的“查看关联错题”同时携带 `userId` 和 `uploadId`。 |
| `subject` | 初始化学科条件；概览学科分布可进入对应学科的错题。 |

例如 `/admin?tab=mistakes&userId=<用户ID>`、`/admin?tab=mistakes&userId=<用户ID>&uploadId=<上传ID>` 和 `/admin?tab=mistakes&subject=<学科名称>`。参数由 `URLSearchParams` 编码。

点击栏目导航会清除关联条件；指定上传批次时显示上下文提示，并提供返回上传批次的入口。栏目、刷新版本或 URL 关联条件改变时，内容区域通过 React `key` 重新挂载。

URL 保存栏目和内容查询条件，包括 `search` 关键词。内容表单提交查询和重置时同步改写 URL，顶部“刷新”读取当前 URL 后重新挂载内容，浏览器前进与后退重新应用条件。用户列表的搜索、权限筛选、排序及分页保存在组件状态中。

## 用户与内容查找

用户列表从 `/api/admin/users` 读取数据，在客户端按用户名、昵称或微信号进行不区分大小写的搜索，并组合角色、启用状态和使用权限筛选。每页显示 20 条，筛选或排序变化时回到第一页；清除筛选保留当前排序。

使用权限按 `trialEndsAt` 判定：`null` 为长期可用；期限晚于当前时间为体验中；期限小于或等于当前时间为体验已到期。界面每 60 秒更新时间依据。排序支持注册时间降序、最近登录时间降序、错题数量降序，默认最新注册优先；从未登录的账号在登录时间排序中按 `1970-01-01` 处理。停用状态与体验权限分别筛选。

错题和上传列表采用服务端分页，每页 20 条，按创建时间降序、唯一 ID 降序排序，保证相同创建时间下的顺序确定。内容表单区分编辑中的条件与已提交条件，提交查询后更新列表并回到第一页。学科选项合并固定科目与概览接口返回的数据库已有学科名称并去重，保留已有名称；学科选项加载失败时提供单独重试。

用户操作使用原生 `dialog`，包含创建、编辑、重置密码、启用或停用、试用期管理与删除。当前管理员不能停用、删除或降级自己，服务端再次校验。删除确认列出账号、错题、上传原图、练习卷、知识点记录与作文报告的清理范围，要求输入完整用户名；提交期间禁用关闭和重复提交。重置自己的密码成功后进入登录页。

## 查询取消与界面状态

`useData` 为每次查询创建 `AbortController`，将 `signal` 传入 `fetch`；URL、刷新版本改变或组件卸载时取消请求，并通过 `active` 标记禁止过期响应写入状态。全部查询使用 `cache: "no-store"`。

查询状态记录对应 URL 和刷新版本。两者与当前请求不符时隐藏旧数据与旧错误，显示加载结构，避免切换筛选后继续展示旧列表。请求失败显示错误和“重新加载”；空结果提示清除条件或调整关键词。加载使用 `role="status"`，错误使用 `role="alert"`。

## 账号更新与数据一致性

以下规则以 `lib/users.ts` 和 `app/api/admin/users/[id]/route.ts` 的当前实现为依据。

- PATCH 先验证请求字段、字段类型、昵称、密码、微信号及试用期操作；拒绝空请求和未知字段。校验通过后，资料、角色、状态、密码、微信号和期限由 `updateUser` 的单条 UPDATE 一起提交。
- 所有登录账号读取共用包含 `session_epoch` 的列定义，查库失败抛出异常，与账号不存在分别处理。提交状态字段或密码字段各使 `session_epoch` 增加 1，同时提交两者增加 2；现有会话随版本变化失效。
- `extend7` 使用数据库执行时的期限，以原期限和当前时间的较晚者为基准增加 7 天。UPDATE 条件要求期限仍非 NULL；并发请求已开通长期权限时，旧延期请求无法覆盖它，同请求其他字段也不会部分写入。`unlimited` 将期限设为 NULL。
- PostgreSQL 事务通过共用 advisory 事务锁与账号行锁检查当前角色、状态及其他启用管理员，防止停用或降级最后一个启用管理员。返回值区分已更新、账号不存在、删除中、已长期可用和最后一个启用管理员。
- 微信号字段未传时保持不变，传空字符串时保存 NULL，列表显示“未填写”。

### 删除账号

删除接口先禁止删除自己，并检查目标账号。通过 `beginUserDeletion` 原子设置 `deletion_started_at`、停用账号并递增会话版本，同时保护最后一个启用管理员。标记后 PATCH 返回 409，不能重新启用或修改资料；删除接口允许继续清理。列表展示删除中的状态并提供“继续删除”。

1. `listUploadFileKeys` 完整读取上传记录与 `upload_objects` 的图片键，严格校验并去重。
2. 根据已持久保存的 multipart 标识中止全部进行中的上传，然后每组最多删除1000个R2对象。失败时账号保持停用，数据库记录保留供重试。
3. R2 清理后，`deleteUserRows` 在 PostgreSQL 事务中检查删除标记与启用状态，再清理账号及其关联记录。数据库外键约束同时保证关联完整性。

图片内容写入前，应用先将 multipart 标识存入 PostgreSQL。账号删除能够中止尚未完成的图片上传，请求进程终止后仍可根据索引清理。R2 与 PostgreSQL 没有统一事务，数据库失败时保留索引以便重试，已删除图片无法恢复。

### 删除上传批次

`lib/admin.ts` 在 PostgreSQL 事务中锁定上传行，严格校验图片键，分组删除 R2 对象，再删除关联错题与上传行。R2 操作失败时回滚数据库事务并保留索引以便重试。跨存储操作不能提供统一事务。单道错题删除保留上传原图。

## 系统诊断

AI 探针复用业务服务的 `/responses` 与 `deepseek-flash`，使用 20 秒超时，不返回上游原始错误内容。探针只验证文本连通性，未测试图片识别。R2 状态仅表示绑定存在，不代表执行了读写探针。

## 验证

验收范围与证据统一记录在 [后台交付文档](../../delivery/features/admin-upgrade/management.md)。实际运行使用本机 PostgreSQL 17.7，现有三个账号、真实作业备份及真实图片。破坏性数据库验证使用独立 schema 的真实资料副本，保留应用数据库中的资料。线上发布与线上数据迁移须单独执行备份、校验和切换。
